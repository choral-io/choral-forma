# Choral Flows Definition · v1 beta 2

Use `dsl: choral/flows-v1-beta.2` to author a fixed Definition. The [Definition Schema](definition.schema.json) defines the grammar. This specification defines references, activation, selection, delivery and observable outcomes.

## Document and public interface

A JSON document or its JSON-compatible YAML representation contains `dsl` and `definition`. A resource-only import may contain `schemas` instead of a Definition. Keys must be unique. Unknown structural fields are errors. `metadata` is inert data. `title` and `description` are literal strings. Step and Definition IDs and connection aliases use the local-name grammar in the schema. Step IDs are unique among siblings. Step list order is for presentation. Case list order affects execution.

A Definition has an `id`, a list of `steps`, optional private child `definitions` and an optional read-only `context` Schema. Its entries are the steps with no incoming step connection in their scope. A step whose only dependencies read `$context` is still an entry. The selected entry receives the caller's argument as its fixed `$input`, validates it against its optional `input.schema`, and must omit `input.bind`. This applies to top-level and child invocations and to the entry receiving a fixed item or round input. Context is supplied and validated separately. An entry invoking a child can forward its context alias in `context.bind`. To combine the caller's argument and context as business data, publish the argument from the entry and bind it alongside an explicit context dependency in a downstream step. A sole entry is inferred. A caller selects one explicitly when there are several. Reordering or renaming an entry can be checked independently: reordering preserves the interface and renaming changes the public entry ID.

A child with a prepared delivery still owes all required work. For example, an intake stage may publish a Handoff and prepare its result while receipt registration is pending. The parent can use the result only after successful child completion. A required registration failure fails the invocation and leaves the final review unstarted.

An ordinary terminal with a formal output that is unconsumed on the successful path is a candidate for flow delivery. Value, success, observation and continuation connections count as consumers. Flatten transparent scopes when finding consumers. Local Watcher steps belong to their owner and their outputs feed that observation. Each selected entry has a consistent obligation across successful paths: exactly one delivered value, or none. Required work must settle before successful completion, even if a candidate value is already available. Multiple eligible values cannot implicitly select a first or last result.

The graph of step definitions may contain a continuation. Each actual execution has its own identity and depends on earlier occurrences, forming a DAG. An unresolved source can still become effective. An excluded branch supplies no value, including no implicit null. A downstream ordinary step can start only when its required connections resolve and it can construct its fixed input. An open wait or an inability to make further progress cannot establish successful flow completion.

## Steps, dependencies and outputs

| Form                                 | Meaning                                                                                                                                                                                             |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ordinary step with `output.bind`     | Construct one formal value from fixed `$input`.                                                                                                                                                     |
| `call: {target, input?, onFailure?}` | Invoke a host procedure. The target is an opaque identifier. Omitted call input passes the fixed step input.                                                                                        |
| `flow: {target, entry?, input?}`     | Invoke a private child by ID or an imported public Definition by `alias.id`. The selected child entry receives the bound input. Its formal result is available only on successful child completion. |
| `judge: {cases}`                     | Select on a fixed input. A final `otherwise: true` case is required.                                                                                                                                |
| `watch: {observe, cases}`            | Adopt source outputs and select on each decision basis until release.                                                                                                                               |
| `each: {items, input, steps}`        | Fix the membership of a list or map and start a body for each member.                                                                                                                               |
| `repeat: {steps}`                    | Start a round with the arrangement's fixed input. A continuation can start a fresh round.                                                                                                           |

`needs` maps a local alias to `{from, require, exit?}`. Several prerequisites of one arrangement enable one logical occurrence when all apply. A source path can cross transparent `each` and `repeat` bodies. A private child's internals and a Watcher's local steps are inaccessible from outside. Child calls expose their public output and completion. A `$context` connection can make the read-only context available as an output dependency. Declaring a Definition `context` Schema makes context part of its invocation contract. A child call to that Definition must supply `context.bind`. An explicitly bound null satisfies a nullable context Schema. A root invocation supplies its declared context at admission.

`require: success` waits for successful completion. `require: output` also binds the source's formal value under the alias. An optional `exit` filter names a declared normal exit or a nonempty list of distinct normal exits. Every exit admitted by an output dependency must be able to supply a value. An ordinary downstream step constructs its fixed input through `input.bind` from its readable dependency aliases, then validates the optional input Schema. A failed dependency, binding or validation does not produce a successful output.

For a call or child call, omitted `output` exports no value. `output: {}` publishes the returned result. `output.bind` may read `$input` and `$result`. Validate the optional common output Schema before publishing success and the value together. A bound null, false, zero or empty list is a real value. Losing a reply or failing to bind an output after an external effect gives no permission to repeat that effect.

Both step `call` and predicate `$call` require a bounded service operation. A procedure may return a business result it can compute during the call, or acknowledge registration of work that will finish later. It must not hold the invocation open for a person to act, a future deadline to elapse or an independently delivered business response to arrive. The bound belongs to the target's service contract. The Definition has no portable timeout duration. A technical error follows the ordinary failure rules unless the call qualifies for tolerance under the rules below. Uncertain registration follows the ordinary failure rules.

Express the external wait with a Watcher. If a request is needed, use an ordinary step to register it and return its acknowledgement. Receive the eventual decision or expiry as a separate submission to a local step with externally supplied input. Registration success alone cannot satisfy a case that requires that event. A predicate call can check available evidence for its snapshot. A Watcher can stay open between events without keeping a procedure invocation open.

## Tolerating a confirmed failure

In a purchase that needs three quotes, supplier D may be worth contacting even when its service is unavailable. Put the declaration on D's call position. Another position invoking the same procedure can use the default behavior.

```yaml
call:
    target: supplier@1
    onFailure: tolerate
```

`tolerate` is the only accepted value. Omitting `onFailure` uses the ordinary technical failure rule. The declaration applies to each occurrence of this position, including a step inside an item, round or child Definition and a local step of a Watcher that executes a `call`. Child invocation through `flow` and decision predicates using `$call` keep their own grammar.

Apply the disposition only when the procedure has actually been invoked and its capability contract establishes a **definite technical failure of that invocation**. The adapter must have enough evidence to distinguish this from an unknown external outcome. The runtime retains an attributable failed occurrence. Its own obligation is settled. It contributes zero successful completions, formal outputs or normal exits. The owning flow may complete successfully once all other required work and its own delivery obligation are satisfied.

| What happened                                                                                                   | Observable consequence                                                                                                                             |
| --------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| The supplier returns a valid “no quote” business response.                                                      | The ordinary output binding, Schema and cases process that response.                                                                               |
| The supplier confirms the marked request failed.                                                                | The step remains failed. A collector can still release based on other suppliers' real outputs if its authored condition permits.                   |
| The connection is lost after dispatch and the request might have taken effect.                                  | The outcome stays uncertain. The normal technical failure rule applies.                                                                            |
| Input admission, argument construction, capability resolution, return-value validation or output binding fails. | The ordinary rule for the failing stage applies. A downstream binding failure cannot change an upstream success into a tolerated provider failure. |

The provider contract and runtime determine how confirmation is delivered and correlated to the invocation. The Definition needs no error payload or failure port. Retries, reconciliation and compensation retain their own contracts.

### Dependencies and public delivery

Evaluate every other obligation independently. A consumer requiring the failed call's success or output cannot start from that call. An undecided route can still make such a consumer required. If its guard later excludes the route, that consumer no longer blocks completion. If the guard selects it, the missing success or output prevents successful flow completion. Timing of failure reporting or the name of an exhausted execution state is a runtime concern.

For example, procurement can hand off the three available quotes while a fifth provider is still working. If an independent audit decision remains outstanding once the fifth provider settles, the owner still waits. Waiving the audit permits completion if the remaining obligations are satisfied. Requiring D's actual quote leaves an unsatisfied audit. A handoff already made remains part of the execution history.

A child whose selected entry owes a value must still deliver exactly one. If the failed call was its only possible producer, even a parent consumer requiring only child success cannot proceed. A child with a completion-only entry can complete successfully once its obligations settle, including an explicitly tolerated failure of an internal call. Its parent can then consume that success. A successful delivery of JSON `null` requires an actual successful producer. The `remaining` policy continues to govern demand for outstanding work.

## Data and expressions

Ordinary JSON values in a value template construct data recursively. Strings are literal. An object containing a dollar-prefixed key must be one of the singleton operators below. A Schema, metadata, literal payload or value returned from a source or procedure is data within its own interpretation boundary.

| Operator   | Behavior                                                                                                                                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `$literal` | Copy the entire value unchanged, including nested dollar-prefixed keys.                                                                                                                                      |
| `$ref`     | Read a permitted root followed by `#` and a JSON Pointer. An empty pointer returns the whole root. Missing roots, absent members and invalid array indices are binding errors. A present null binds as null. |
| `$expr`    | Supply explicit `lang`, fixed `code` and a map of named `args`. Authorize and resolve the arguments before evaluating. Only the bound arguments are visible as workflow data to the expression.              |
| `$call`    | In a judgment predicate, including its expression arguments, invoke a host target with an explicit `input`. Adopt and record its result for that evaluation. A skipped case evaluates none of its arguments. |

Value reference tokens decode `~1` as slash and `~0` as tilde. Reading `decision#/approved` fails for `{}` or a null parent, and succeeds with null or false for a present member carrying that value. To inspect an optional member, an author with access to the parent can bind `d: { $ref: "decision#" }` and use CEL `d != null && has(d.approved) && d.approved == true`. Permission to read the whole parent is checked at binding. [JSON Pointer](https://www.rfc-editor.org/rfc/rfc6901)

Each expression declares `lang: choral-cel/v1`. This denotes the full standard CEL language at the pinned upstream revision, with the Choral data boundary described here. It has no document-level default. A predicate must produce a Boolean. A binding error, evaluation error or non-Boolean predicate fails the decision. Input strings never become source code. The host supplies an isolated evaluator and enforces access and resource limits. Future host functions must preserve standard meanings and require explicit host support. [CEL v0.26.0](https://github.com/cel-expr/cel-spec/releases/tag/v0.26.0)

Validate the source value against its contract before binding. A numeric value declared as JSON Schema `integer` binds to CEL `int`. A value declared only as `number`, or with no Schema, binds to `double`. Decimal spelling does not determine the type. The observation field `count` is an integer. Apply the safe-integer bound −(2⁵³−1) through 2⁵³−1 to integer-valued ordinary JSON inputs and outputs before lossy conversion. A JSON delivery must satisfy its declared contract. The following interoperability cases use the original JSON number spellings.

| JSON input               | Source Schema                 | Required outcome                                |
| ------------------------ | ----------------------------- | ----------------------------------------------- |
| `3`, `3.0`, `3e0`        | `integer`                     | CEL `int(3)`                                    |
| `3`, `3.0`, `3e0`, `3.5` | `number` or absent            | CEL doubles 3.0, 3.0, 3.0 and 3.5 respectively  |
| `3.5`                    | `integer`                     | Input Schema rejects the value                  |
| `9007199254740992`       | `number` or absent            | Out-of-range input error                        |
| `9007199254740991`       | `integer`, expression `n + 1` | Out-of-range result at the JSON output boundary |

For integration testing, parse each `inputJson` string as the original input, apply its optional Schema, bind the result to the CEL argument `n`, and compare the delivered JSON value or error stage. This preserves the distinction between the source spellings when testing different language adapters. [Numeric binding cases](../tests/fixtures/numeric-binding-cases.json)

A direct value binding preserves the JSON value through handoff, storage and readback. Numbers compare by mathematical value, so their spelling can change. Validate authored Schema limits and instance values before converting an expression argument. For example, `1.0000000000000001` satisfies a `number` Schema with `exclusiveMinimum: 1`. A direct `$ref` still delivers that value. In a judge or Watcher, passing the same number to `choral-cel/v1` as `n` yields a double for which `n > 1.0` is false. This conversion applies only to the expression argument. [Host acceptance vectors](../tests/fixtures/handoff-and-replay-cases.json) · [JSON Schema instance equality](https://json-schema.org/draft/2020-12/json-schema-core#section-4.2.2)

For a numeric argument, use the contract at the source of the read (for example the fixed input's `input.schema` or a report's declared output Schema). Project that contract to the selected object member or array element. A child’s selected formal delivery supplies the source contract for its caller’s `$result`. An untyped procedure reply follows the no-Schema rule. A step's `output.schema` validates its published value after binding. At a numeric leaf `integer` admits the integer category, `number` admits both integer and fractional categories, and other declared types admit neither. An absent type admits both. A type list admits the union. Follow resolved Schema references in their owning resource. Intersect restrictions from siblings and `allOf`; union the alternatives of `anyOf` and `oneOf` before intersecting with their siblings. Use `int` only when the remaining numeric category is exclusively integer. Thus nullable integer binds 3 as `int`, and alternative integer/number binds it as `double` in either branch order.

Apply the same projection along the actual property or item path using `properties`, matching `patternProperties`, `additionalProperties`, `prefixItems` and `items`. A branch excluding the actual container type contributes no numeric category. A Boolean false Schema contributes none, true contributes both, and revisiting the same Schema at the same path adds no narrowing. Other validation keywords still constrain admission but do not select a CEL type. For example, `multipleOf: 1` alone leaves the type `double`. A host can perform this projection after normal Schema validation without choosing a winning union branch.

## Observation and selection

Every Watcher observes at least one upstream step, including through a collection. This applies inside child, item and round scopes. Declare each source under a distinct key in `watch.observe`. The key names the observation view. An inline step also takes that key as its local ID.

| Source                           | Example                                                 | Association                                                                                                                                              |
| -------------------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| External single step             | `plan: {from: prepareReview}`                           | The upstream step occurrence associated with this Watcher.                                                                                               |
| Members of an external expansion | `reports: {from: assignReviews, collect: submitReport}` | The named member step of the associated `each` occurrence. A member path may cross transparent scopes. Declare separate observations for separate steps. |
| Local ordinary step              | `confirmClose: {input: {}, output: {bind: true}}`       | A step owned by this Watcher occurrence. It can also use an ordinary procedure or child call.                                                            |

A connection has `from` and optionally `collect`. An inline step uses its ordinary input, dependencies, operation and output. A local `needs` names a source in the enclosing execution scope. With `input.bind`, the Watcher starts one logical invocation after opening and once those dependencies are ready. Recovery and new observations preserve that invocation. With externally supplied `input` (no `bind`), each distinct admitted submission supplies the fixed input for one invocation. The host addresses the definition revision, instance, open Watcher occurrence and local step, checks the actor and enforces the declared input Schema. Replay of an admitted submission does not invoke it again.

An observation exposes `known` (association established), `count` (number of adopted formal outputs) and `results` (their values). Adopt existing eligible outputs when associating and subsequent outputs while open. Deduplicate by source occurrence within that observation. Preserve first adoption order, fix an order for outputs adopted in the same batch and retain that order on replay. Two occurrences returning equal values contribute twice. An established empty expansion has `known: true` and zero results. Association does not imply an eventual result count. A report from an earlier round belongs to its original expansion even if the same reviewer participates again.

In the host acceptance vectors, each string ending in `Json` carries the original JSON text. Check the direct delivery after readback, then evaluate the expression independently on the original input. Each replay sequence starts with a fresh open observation and supplies one submission at a time.

Within one observation, match a redelivery to its source occurrence first. For a known occurrence, compare the payload with its adopted JSON value, including nested values. An equal payload leaves the count, order and decision unchanged. A different payload conflicts with the immutable fact and must be rejected. Distinct occurrences with equal payloads each contribute one result. Thus replaying one report as `3.0` after adopting `3` preserves one report, while a second report with value `3` brings the count to two. Boolean `true` and number `1` are distinct. [Replay acceptance vectors](../tests/fixtures/handoff-and-replay-cases.json)

An observation connects a source to the Watcher. It does not guard entry to the Watcher's own scope. When that scope is active, the Watcher can open even if all observed upstream alternatives are known to be absent. A local step's unsatisfied `needs` prevents its submission but does not close the Watcher. To wait only on a selected branch, invoke a child containing the Watcher through an exit-filtered connection, or give the Watcher a case that releases it on the other branch.

Evaluate cases when the Watcher opens, using all facts adopted at opening. While open, evaluate again when an observation changes, including when an empty expansion becomes known. Apply each adopted batch as one snapshot. The host records its batch boundaries and order. Redelivery of the same facts preserves the existing decision and cannot repeat an external predicate call. `on` observes fresh output presence during that batch. A case needing a specific external action can give that action its own local step with an input contract. Reading the cumulative `results` of a step that accepts several actions can also see actions from earlier batches.

Scope the Watcher to the effective arrangement in this Definition invocation and its owning item or round. It can open before any reports arrive. Record which issuing occurrence owns a result when associating it, including a timer or manual submission. A delayed external judgment is evidence for the snapshot on which it was requested. Reusing it for a changed snapshot requires applicability under that procedure's contract. A changed snapshot alone does not retire a still-required call. Its technical failure follows the normal failure rule.

If a Watcher has already adopted a fourth report when approval of the first three arrives, a contract limited to those three supplies no approval for the current four. A contract that explicitly covers the appended report can authorize release on the four-report snapshot. Bind the selected output to that same snapshot. A Boolean reply alone establishes no transfer of approval, and receiving a stale reply gives no authority to repeat an effectful call. If the Watcher released on three before adopting the fourth, its three-report output remains final.

A submission can be admitted only while its Watcher is open and the local step's `needs` are ready. An early submission creates no invocation and a later dependency change does not replay it. By contrast, an admitted submission that produces output can leave the Watcher open when its case predicate is false. Neither outcome implicitly queues a future confirmation. An external system that promises reliable delivery must arrange delivery to the intended open occurrence, for example by retaining the event until admission is possible. A transport acknowledgement alone is not evidence of Watcher adoption. A delivery after closure cannot create a new local invocation or be redirected to a successor merely because it is now active.

Readiness of a local step's dependency does not establish that the Watcher has already adopted that dependency's output under a separate observation alias. A case reading the alias uses the results present in its decision snapshot. If either of two observations can arrive first, handle the empty list and arrange to reconsider the case when the other observation changes.

At each decision, use one authoritative snapshot. A case with `on: localId` is eligible only when the snapshot newly adopts a formal output from that local step. Presence of a prior confirmation, registration of a timer and truthiness of the new value do not trigger it. Evaluate eligible cases in declaration order. Each case has a `when` predicate or a final `otherwise: true`. A Watcher may omit `otherwise` and keep waiting. A fixed-input judge may select `raise: {}` or bind a reason with `raise.bind`, failing its owning invocation without a normal exit. Expected business declines can use normal outputs.

A normal case declares an authored `exit`. Select a shared step-level `output.bind` or a case-local `output.bind`. Apply any common output Schema to the produced value. In shared Watcher output, copy each external observation's complete `alias#/results` group once into the result map. Local groups may also be copied. Case-local bindings use the frozen basis. Publish the exit and validated output together. A case without a shared or local binding can publish success without output. Close the Watcher on release and end its demand on its sources. Late inputs or late timer callbacks cannot change the frozen result.

In the five-reviewer example, a click at two reports is admitted and the Watcher waits. The third report alone does not reactivate that click. A fresh click at three selects `confirmed`. On a snapshot with the fifth report, a click and timer completion, `all` wins by authored order. At three reports a simultaneous click and elapsed timer select `confirmed`. With zero reports the timer releases `deadline` with an empty report list.

## Expansion, repetition and completion

`each.items` reads the arrangement's fixed `$input`. Freeze a list's indices or a map's keys when creating the expansion. `each.input` uses `$input` and `$item` (with `key` and `value`) to construct each member's entry input. Equal values retain separate membership. The body receives its own fixed input. An expansion or repeat has no implicit aggregate output or completion event.

Ordinary `needs` can combine sources from the same item or round with sources from its enclosing occurrences. Independent expansions or repeats supply no implicit pairing between their members, even after ordinary forwarding steps. Use a common item or round for per-member joins, or collect the outputs of each expansion before explicitly matching their values.

The transparent `each` or `repeat` body has an inferred entry. The initial round of a repeat receives the arrangement's bound input. An ordinary step directly inside that repeat can declare `continue: $repeat`. Its successfully constructed formal output supplies a fresh round and is consumed by that continuation. A repeat inside an item belongs to that item. Redelivery of the same continuation step occurrence's success reuses its successor round. Independent effective continuations can create independent successors, including when their outputs are equal. Earlier rounds can still be active. A continuation and an outward connection can both consume the same success. Same-occurrence dependency cycles are invalid.

For an `each` containing a `repeat`, associate a receipt with its issuing step occurrence, including the enclosing item and round. Redelivery uses that original association even if another item is now in a later round or returns an equal value. A downstream `collect` of a nested step counts its distinct successful outputs. To wait for every item, the authored paths must guarantee one selected output per item, or the predicate must check coverage of the fixed membership. Two distinct successes from the same item can otherwise satisfy a count of two.

Retained work is required by default. `remaining: end-when-undemanded` allows logical ending once all effective and future demand for that work has ended. An `each` may declare this policy collectively for unfinished member work, including member Watchers. A different consumer can keep that work required. Logical ending carries no successful output and makes no guarantee of physical cancellation. Failure of retained work can still fail the flow after another step has produced its delivery. A technical failure propagates by default. A procedure call may tolerate a confirmed failure under the rules above. The profile has no step-level `fail`, failure dependency or `propagate` disposition.

When two stages can consume the same call occurrence, directly or through an explicit handoff, the first Watcher's release removes only its own demand. A declared path that can still require the result for the second stage keeps the call required even when no Watcher currently observes it. Once that path is definitively excluded, the call may end logically if its policy permits it and every other effective or reachable consumer has also ceased to need it. This is the earliest permitted ending. An implementation may let the call finish. Apply the same check separately to any unfinished upstream work.

## Contracts, imports and host admission

Business contracts are JSON Schema Draft 2020-12 objects or Booleans. A Schema-position `$ref` may name a resource in document-level `schemas`, an explicitly imported `alias.Name`, or a pointer inside its owning Schema. Named references in an imported contract resolve in its original document. Missing names fail resolution. `imports` maps an alias to a locator resolved by the host. A child call targets a private direct child by ID or an explicitly imported document's public Definition by `alias.id`. Imported definitions keep their own schemas and import namespaces. [JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12)

Every document in an import graph must use `choral/flows-v1-beta.2`, including schema-only resources. Before starting an instance the host must support the profile and resolve contracts, expression languages and procedure targets at their use sites, including in conditional paths, local steps and called child definitions. Resolution checks availability without invoking a target, admitting a submission or evaluating an expression. Reject startup on an unsupported requirement and report the identifier and offending location. Target names are opaque. The host must supply an implementation that meets the bounded-call contract, which a structural checker cannot infer from the name. The profile has no separate capability list or general executable extension declaration. Descriptive metadata is ignorable. Required admission policies must be understood and enforced by the host.

Prefer a local step when one scope exclusively uses it and each occurrence of that scope owns its work. Shared work or work with an independent lifetime can live in an enclosing scope. This is authoring guidance.

## Checking a Definition

The [Definition Schema](definition.schema.json) checks document structure. Host admission also requires semantic checks for aliases, imports, readable roots, exit filters, local sources and possible entries and deliveries. Actual delivery cardinality can depend on the path taken at runtime.

The [crate README](../README.md) documents the subset supported by `validate_definition` and provides runnable examples.
